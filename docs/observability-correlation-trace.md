# Observability & the correlation trace (LAW / App Insights)

**Agenda item:** LAW / App Insight
**Backlog:** WI-06

This chapter shows Kaiser Permanente how to make an agentic workflow **observable**: every run is
traceable end to end by a single correlation ID, from the first tool call through the policy
decision to the human approval. The workshop ships a runnable local model of this and maps it 1:1 to
the durable Azure services.

## What ships in the reference app

Every request carries an `x-correlation-id` (generated by the backend if absent, echoed on the
response and forwarded to the agent service). Two complementary surfaces expose it:

| Surface | Purpose | Code |
| --- | --- | --- |
| **Activity log** | Flat, capped feed of recent backend activity (invoke, HITL, HTTP, warnings) for the live UI panel. | `backend/src/logs/logBuffer.js`, `GET /api/v1/logs` |
| **Correlation trace** | The **complete, ordered event list for one run**, keyed by correlation ID. | `backend/src/observability/traceStore.js`, `GET /api/v1/traces/:id` |

### Event taxonomy

The trace store records a stable set of event types so a run reconstructs deterministically and the
names map directly to App Insights custom events:

| `type` | Emitted when | Key fields |
| --- | --- | --- |
| `run.started` | invoke received | `source` (agent-service/local/local-fallback), `riskTier` |
| `tool.called` | each MCP tool call | `name`, `decision` (allow/redact/review_required), `latencyMs` |
| `agent.handoff` | each specialist hop | `name`, `role`, `status`, `handoffTo` |
| `policy.decision` | guardrail resolves | `decision` |
| `run.completed` | invoke returns | `requiresHumanReview` |
| `review.created` | HITL task registered | `status`, `dueAt` |
| `review.transition` | human/system HITL action | `action`, `actor`, `to` |

Example (abridged) from `GET /api/v1/traces/{id}`:

```
 1 run.started        invoke        source=agent-service riskTier=High
 2 tool.called        patient.get   decision=redact  latencyMs=118
 5 tool.called        protocol.search decision=allow latencyMs=242
 8 agent.handoff      Discharge Transition Orchestrator → Case Context Agent
16 policy.decision    review_required
17 run.completed      requiresHumanReview=true
18 review.created     PendingReview
19 review.transition  approve by Nurse Alex → Approved
```

## Demo script (chapter 06)

1. Invoke a case; copy the `x-correlation-id` from the response header.
2. `GET /api/v1/traces/{id}` → walk the ordered event list; point out the `tool.called` policy
   decisions (`patient.get → redact`) and the escalation path on P0310.
3. Approve or reject in the UI, then re-fetch the trace → the `review.transition` event with the
   reviewer's name appears at the end.
4. Show the live **Backend activity log** panel updating in real time as you act.

## Graduating to Log Analytics / Application Insights

The in-memory trace store is a **teaching model** — it is process-local, capped, and lost on
restart. In production the same taxonomy becomes durable telemetry:

- Instrument the backend and agent service with the **Application Insights SDK** (or OpenTelemetry
  exporter). Emit each event above as a `customEvent`, and set the **operation/correlation ID** to
  the workflow's `x-correlation-id` so all events for a run share one operation.
- Put per-event fields (`decision`, `latencyMs`, `actor`, `status`) in `customDimensions`.
- Ship to a **Log Analytics Workspace**; query by correlation ID:

```kusto
customEvents
| where customDimensions.correlationId == "trace-…"
| project timestamp, name, customDimensions
| order by timestamp asc
```

- Build workbooks/alerts on the same fields: tool latency, `policy.decision == "escalate"` rate,
  time-to-approval on `review.*`, and fail-closed counts.

### Why this matters for KP

- **Auditability:** a governed workflow must be reconstructable after the fact — the correlation ID
  is the single join key across agents, tools, policy, and the human gate.
- **Safety monitoring:** escalations, redactions, and rejected transitions are first-class events,
  not log spelunking.
- **Portability:** the taxonomy is defined once and works locally and in App Insights, so the
  workshop artifact and the production system speak the same language.

> Note: the local buffers are process-local and not durable. Treat them as a demonstration of the
> pattern; Log Analytics / Application Insights is the system of record.
